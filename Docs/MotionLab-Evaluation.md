# 动作路线实验评估

日期：2026-10-10。本文记录独立实验基线与未通过项，不是日常接入批准或动作自然度验收。

## 可复现环境

入口：Unity 菜单 `VirtualPartner > Motion Lab > Open experiment panel`；场景 `Assets/Scenes/MotionLab.unity`。具体环境、权重来源、命令和接口见 [实验说明](../Tools/MotionLab/README.md)。角色副本通过现有 ActionCoordinator 播放，日常 PhoneOS、Momotalk、历史、Memory 与服务配置不变。

机器：i7-9750H、16 GB RAM、GTX 1650 4 GB；Unity 6000.3.12f1。模型安装在 F:/Project/MotionExperiments 的独立环境。GPT-SoVITS 使用原 CPU 配置；并发结论仅适用于该配置及当时其他桌面负载。

固定语料包含左右、高低、挥动次数、摊手、指向、双臂配合、头部前倾、浅蹲、保持、局部接管和中断。语义路线的 11/22/33 是重复编号，DeepSeek 请求没有确定性种子；本地生成模型记录实际种子。

阶段计时：语义解析中位数 1.26 秒（36 次）；MoMask 暖推理中位数 0.68 秒（36 次），两种官方 100 迭代 BVH 转换合计中位数 6.12 秒。DiP 当前角色前缀 5 步每段约 0.21 秒、10 步约 0.43 秒的中位数；这里每段为 40 帧/2 秒，统计同时包含冷段，不能等同于从点击到角色响应。完整分布以 `summary.json` 为准，P95 使用 nearest-rank，冷启动和最大值保留。

早期工具等待重复暖推理和两种 BVH 转换结束后才播放，产生额外项目侧等待。现在首份原始位置输出原子发布后即允许播放，后台继续完成原有诊断转换；没有降低生成质量或省略失败样本。模型导入/加载仍在冷启动路径上，不宣称已完成低延迟常驻服务。

## 实际动作与适配问题

1. 修正了重定向 FK 对未映射父节点使用静态基姿态、而最终角色仍受 Idle 驱动的问题。修正后 52 条学习式主样本的映射骨段方向最大误差约 0.028°，骨段长度变化 0。该指标只说明方向转换，不证明动作语义正确。
2. MoMask 主样本最终脚部位移中位数约腿长 6.2%，最差约 293%；源输出本身也有相近移动，不能仅归因于重定向。DiP 同样存在明显脚部移动。这里是全段足部位移，包含真正迈步，不是只统计接触阶段的脚滑。
3. MoMask 的“摊手表示疑问”样本中可见双臂举高；部分左右/高度/顺序变体和浅蹲没有形成足够清晰的目标姿态。语义路线的手部目标较可控，但头部“向左转”不能凭局部 Y 轴数值判定正确；角色轴标定仍需改进。
4. 位置序列无法唯一确定手腕扭转。源骨架有动作，不代表当前角色有正确掌心朝向。完整关节范围、物理平衡、布料与精确接触均未通过；当前重定向只提供诊断和官方脚部 IK 对照，没有暗中大幅修正成另一动作。
5. DiP 的当前姿态前缀已转换，但采样有编辑器时序间隙，角色与训练骨架比例差异明显；接段位移/速度变化另存 `source-diagnostics.json`。这仍是接续适配原型，不能称作可用的连续角色控制器。
6. 语义路线补充了最终 Transform 测量，排除旧帧目标，并与求解缓冲区报告分开。无 `finalGeometrySamples` 的零值不算零误差通过。头/躯干直接旋转不属于末端位置指标的覆盖范围。

最终语义复测中，33 条含末端采样的记录最大位置误差约肢链长 0.070%，但这只统计实际可执行的目标；`07_dual` 三次均报告左臂目标超过可达误差限制，属于部分动作失败，不能算双臂意图通过。三个头部/躯干样本没有末端采样。这些失败仍保留，不通过放宽阈值掩盖。

所有样本需观看完整录像确认次数、顺序和自然度；拼图只作索引，不替代视频验收。

## 语音并发与失败

早期测试出现过 NumPy API 不兼容、前缀张量类型错误、模型重复加载/内存不足；各自修复后另建复测目录，原失败不删除。两次 MoMask 并发记录明确报 CUDA out of memory，其中系统可用 RAM 不到 1 GB；不能仅凭该异常就断言模型固有显存需求超过 4 GB。

上一轮 TTS 上游退出后，后续样本出现连接拒绝；另有 Play Mode 退出导致录制中断。这些条目均标记失败/阻塞/未完成。`completed` 只表示测试循环结束，必须同时有真实音频、相关身体动作且无错误才能算音画运行成功；文字回退不算音频。

恢复服务后的初步证据：MoMask 首动作 49.22 秒、首音频 40.82 秒；DiP 首动作 29.69 秒、首音频 33.20 秒，均为冷进程、有录屏并发样本，无音频欠载。语义路线无录屏动作先行样本首动作 1.78 秒、首音频 19.35 秒。三者至少各有真实并发成功证据，但学习式路线的冷启动远未达到目标。不同运行负载和小样本不能据此给出稳定 SLA。

### 冷启动耗时拆分

| 阶段 | MoMask `232757` | DiP `232955` |
|---|---:|---:|
| 已计时模型创建/权重加载 | 16.95 秒 | 17.18 秒 |
| 首次文本编码 | 2.14 秒 | 3.96 秒 |
| 首次动作生成（排除文本） | 4.70 秒 | 0.62 秒 |
| 第二段文本+生成 | 不适用 | 0.50 秒 |
| 其余未细分开销（差值估算） | 约 25 秒 | 约 7 秒 |

未细分部分包含依赖导入、初始化、数据处理、进程和 Unity 交接，尚不能逐项归因。MoMask 的暖重复推理与两种 BVH 转换继续在首份输出后运行，不混入上述首次动作生成。常驻模型、预加载和预热应成为后续低延迟验证的候选，但尚未实施为生产服务，不能把暖核算时间直接当作端到端承诺。

TTS 首音频等待发生在服务返回前；Unity 收到字节到播放的差值很小。目前未细分服务端文本处理、声学生成、声码器和分段输出耗时，不能仅凭 CPU 配置断言是哪一个内部模块占大头。动作与 TTS 并发；语音同步时主要动作需同时满足动作就绪与真实音频开始，不能把两者总耗时简单相加。

录像为 Unity 实际相机画面、按时间戳编码的无声视频。真实播放事件、音频首字节、缓存状态、欠载和失败另行记录。录屏时 ReadPixels 的开销使帧时间尾部升高，需与无录屏结果分开看。

## 检查与交付边界

- Python 数据契约 3 项通过：左右反射、不改原始输出、非有限值/骨架形状拒绝、完整固定语料与原子结果写入。
- Unity 独立环境 6 项通过；生命周期 9 项通过，含到位后定时保持、持有到期释放、局部接管、Debug 优先级和中断。
- 修复实验播放器跳过定时保持间隔的问题。原 LLM 输出仍保留；部分输出本身重复“到位”步骤，可能延长总保持，不能将播放器修复等同于语义时长准确。
- 官方示例可导入、源与目标可对照，但完整已知动作的重定向标定门槛尚未通过。关节限幅、双脚约束、连续姿态接续及全身自然度仍是后续问题。
- 未改日常业务链路，未接入用户历史或长期记忆；真实并发完成后停止本次启动的 TTS 服务，保留原配置。

源码之外的完整数据以外部证据包为准，包含 HTML 索引、原始输出、全部视频/帧、依赖版本、权重哈希、失败条目与文件校验清单。不要只取成功截图作为评估结论。

## 建议与下一步

**优先继续语义目标控制，保留学习式模型作为候选。** 依据是当前语义路线已有更短端到端响应及保持/局部接管基础；不是认定其自然度已胜出。先补齐头/躯干标定、准确的保持时序、末端朝向与脚底支撑，再由用户评价完整动作。

MoMask 可继续用作完整动作片段的质量候选；如果用户更认可其自然度，再评估常驻加载和有限片段如何接入交互生命周期。DiP 推理快，但当前前缀转换、站立约束和方向接续未成熟，应先解决这些问题再考虑常驻服务。

语音等待主要发生在实际首音频之前。动作先行能避免这部分等待，但表达动作是否需要与声音对齐仍由用户选择；不改写 GPT-SoVITS，也不把文字回退伪装成真实声音。

本轮尚不选择正式生产路线。用户需观看完整样本、确认动作语义与自然度，再决定速度取舍和默认音画同步方式。
