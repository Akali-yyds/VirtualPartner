# “跳个舞吧”前两段腿部未播放：定位与修复

日期：2026-10-12。范围：独立 MotionLab；未改动日常 Momotalk、StagePlan、FSM 或语音服务。

## 原因与证据

用户原请求保留在 `F:/Project/MotionExperiments/Evidence/Playground/20261012-012040-951/jobs/20261012-012407-506-a9ed93/`。同一会话多次请求具有相同问题：前两段 `parts` 为双臂、躯干、头，第三段才包含 `support`（骨盆及双腿）。

MoMask 输出包含完整骨架运动，但重定向器把主要动作部位当成严格播放遮罩，过滤前两段下肢数据。源骨架仍完整显示，因此出现源骨架弯腿、角色腿部只响应 Idle 的差异。第三段约在提交后 7.48 秒开始，恰好恢复 support 播放。主要原因不是模型尚未算好腿部，也不是足部接地修正锁死。

另一个交接缺陷：连续段复用同一骨骼占用身份，后一段不写入的骨骼可能继续保留前一段姿态。

## 修复

- `parts` 表示动作重点、保持目标与显式接管目标。新增 `playbackScope`：默认 body，保留生成结果中全身配合；用户明确限制局部运动时使用 parts。
- body 模式扩展到空闲控制组，但不覆盖未被明确接管的已有保持。已有样本缺省使用 body，可用同一输出复测。
- 段落独立持有占用身份；切段时原普通占用平滑释放，新段从当前可见姿态接入，未使用的部位不再停留旧姿态。显式保持身份独立，不随普通段释放。
- 已有保持在候选动作成功写入后才退役，不在进入新段时提前删除。
- 规划提示明确全身律动包括支撑组，区分动作重点和局部限制；让 MoMask 描述正常人体动作，Q 版适配交给 Unity。
- 最终角色诊断记录实际播放部位，便于定位类似问题。

涉及 `motion_planner.py`、`MotionAdaptationProfile.cs`、`MotionLabRetargeter.cs`、`MotionLabDriver.cs`，以及 Python 和 Editor 回归工具。

## 验证

- Python 自动检查 14 项通过，含默认全身配合、显式局部遮罩、非法范围拒绝及原流式/保持检查。
- Unity 编译完成。同一原始第一段执行严格部位遮罩与修复后 body 的对照，证据在 `VirtualPartner/Library/MotionLab/adaptation/scope-test-20261012-012902/`。
- 对照测量来自协调器提交后的真实 Transform；从 0.5 秒后的首个采样姿态计算，左右小腿最大旋转变化由约 7.2° / 15.7°（Idle）变成约 63.1° / 26.2°（生成动作）。这是实际下肢播放证据，不等于舞蹈自然度通过。
- 真实重发“跳个舞吧”：`F:/Project/MotionExperiments/Evidence/Playground/20261012-012838-831/jobs/20261012-013000-379-e3548e/`。三段均有 support 与 body 范围，实际诊断确认第一段即有腿部运动，完成三段播放。
- Editor `scope-test` 另覆盖已有保持不被全身配合抢占、明确接管、全身切局部后的旧腿部占用释放。结果以每次执行目录的 `complete.json` 为准；没有完成文件不可记为通过。
- 最终复测 `scope-test-20261012-013402/complete.json` 确认 4 项范围契约和 5 项实际运行占用断言通过。保持求解回归曾暴露四元数单位长度漂移，已在实验保持求解缓冲中归一化；最终复测新增四元数警告、编译错误及异常均为 0，见同目录 `console-check.json`。

仍需人工评价舞蹈自然度；已有穿模、头部适配和接续质量问题不在本次修复中冒充解决。当前实验仍不承诺复杂舞步、跳跃或完整动态平衡。
